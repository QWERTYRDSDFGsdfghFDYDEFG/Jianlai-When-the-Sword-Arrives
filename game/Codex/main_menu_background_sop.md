# 主菜单主题背景两次制作复盘与固定 SOP

适用范围：以后所有主菜单、章节标题背景、可循环场景背景的重新设计与动态化。

当前状态（2026-09-19）：标题采用夜湖、湖畔相聚、书院送别三张序章纯场景，随最后成功保存或读取的进度变化，当前后续章节沿用送别场景。旧原创主题、候选和测试图片已按批准清单删除；《哀鸿》逆向成果已按用户要求移出，项目不再引用。当前采用状态以 `character_image_index.md` 第 3.2 节为准。下文为带日期的历史复盘，旧图路径、预览与当时的“当前使用”不代表仍可用或获准恢复。

历史设计方向（2026-09-06）：用户当时要求“人物 Live2D＋动态场景”，场景与构图重新设计。前两次复盘用于继承制作方法，不限定新背景或排除 Live2D。概念图采用状态和已否决参考以 `character_image_index.md` 第 3.2 节为唯一记录；出新稿前先核对该节，排除已否决图及其方案。

新方案画面命题的连载同期讨论依据与暂定提案见第 8 节，人物表演空间讨论见第 9 节，三稿构图逻辑与灰阶小稿制作规格见第 10、11 节，标题与菜单制作讨论见第 12 节；记录不等于命题、空间、构图或 UI 方案已获采用。

---

## 1. 最终结论

主菜单不是一张先画完、再把按钮压上去的插画。它同时承担四件事：

1. 在数秒内说明游戏的地点、情绪与核心矛盾。
2. 给标题、菜单和版本信息预留稳定的阅读区域。
3. 用空间路径引导玩家视线，而不是依赖角色立绘抢注意力。
4. 用少量可循环的环境运动建立生命感，但不能妨碍操作。

第二版环境主题采用的路线是（新人物方案另需角色分层、建模与运行时验证）：

`叙事命题 -> 灰阶构图 -> UI占位 -> 无字背景定稿 -> PSD真分层 -> Ren'Py统一循环 -> 逐帧与实际页面验收`

不是：

`先画完整人物图 -> 强行拆局部 -> 直接上Live2D -> 发现破绽后反复补洞`

## 2. 第一次制作：人物主题为什么效率很低

### 2.1 当时采用的方向

- 目标接近“哀鸿式动态主题背景”的表面观感。
- 画面核心是湖边人物、古代书生书箱、头发、刘海、眨眼、衣带和衣摆。
- 先有接近完整成图，再尝试把眼睛、头发、衣带、衣摆等局部拆开。
- 同时尝试 ATL、帧序列、Live2D Cubism 和 Ren'Py 运行时接入。

### 2.2 根本问题

#### 主题表达错位

人物占据绝对重心，但“规矩、选择与代价”以及书简湖的空间关系没有被快速说明。没有读过原作的玩家容易先问“这个人是谁、为什么站在这里”，而不是进入书简湖的处境。

#### 构图顺序反了

标题和菜单是在美术之后寻找空位，导致画面主体、人物视线、书箱、衣带和菜单互相竞争。UI不是构图的一部分，只是后贴上去的信息层。

#### 原图不具备动画生产条件

完整成图中的头发、刘海、眼睑、衣带和衣摆没有真实的遮挡补绘、根部结构与运动余量。把它们从一张合成图中裁出来，不等于得到可动画资产。

典型后果：

- 眨眼时上下眼睑关系错误，出现脸部跳动或重影。
- 刘海与额头、侧发与脸颊的遮挡关系在运动中断裂。
- 发梢、衣带和衣摆根部没有可靠锚点，运动后像漂浮贴纸。
- 原图隐藏区域没有补画，稍微变形就露出透明洞、接缝或重复纹理。
- 试图用蒙版和局部补丁修复时，一个问题会转移到相邻帧。

#### Live2D 使用过早

Live2D适合已经完成严格部件拆分、补绘和网格规划的角色模型。它不能自动把一张完整插画变成可靠模型，也不能替代缺失的美术结构。

第一次制作把大量时间消耗在：

- 眼睛关键点和开合状态。
- 刘海、侧发与头部变形器。
- 衣带、衣摆的根部变形器。
- 模型导出、运行库与 Ren'Py 接入。
- 每次局部修正后重新检查漂移、断层和边缘。

对一个主要依靠远景环境氛围的主菜单来说，这些成本没有转化为更强的主题表达。

#### 文件管理失控

`Scene1_000.png` 至 `Scene1_100.png` 一类帧序列、多个 v6/v7/v8 局部裁图、蒙版、图集和调试图被放入项目目录，造成：

- 很难判断哪一张是当前正式资产。
- 每次返工都增加文件，而不是替换工作区中的临时结果。
- 运行时资产、源文件、实验文件和 QA 文件混在一起。
- 清理成本不断上升。

### 2.3 第一次制作留下的长期禁则

- 不用“复刻另一个作品的动态形式”代替本项目的叙事命题。
- 不从一张合成图反向制造复杂角色模型。
- 没有遮挡补绘、根部结构和运动余量时，不进入 Live2D。
- 环境主题不为眨眼、头发和衣摆建立角色级 Live2D 管线。
- 不把帧序列、自动编号图和 QA 截图放入 `game/`。
- 不把每次试验都升级为永久 `v1`、`v2`、`v3` 文件。
- 不在背景定稿后才决定标题和菜单位置。

## 3. 第二次制作：“书简湖入局”为什么成功

### 3.1 先重新定义主题

新主题不再依赖特定角色知识，而是直接呈现：

- 玩家位于湖外，正准备进入群岛。
- 一叶渡船从画面底部驶向湖心。
- 主岛是第一段旅程的明确目标。
- 群岛、雾、水面和孤灯共同构成“进入一局”的空间隐喻。

因此，即使玩家没有读过原作，也能理解“从外部进入一个复杂地方”的基本情境。

### 3.2 灰阶构图先行

先制作三张纯灰阶构图小稿，只判断：

- 视觉重心在哪里。
- 标题是否有稳定留白。
- 菜单是否有稳定负空间。
- 前景、中景、远景是否清楚。
- 视线能否沿“渡船 -> 主岛 -> 标题”移动。

最终选择 B 方向并发展为 B2 定稿。此时不制作文字、不制作菜单、不制作复杂动态。

### 3.3 美术与代码 UI 分离

背景只负责湖、岛、雾、水光、灯火和空间；标题、菜单、版本号全部由 Ren'Py 绘制。

优点：

- 修改标题文案不需要重画背景。
- 菜单位置、颜色、悬停状态可以独立调整。
- 分辨率缩放和本地化不会被烘焙文字限制。
- 可单独检查背景运动，也可单独检查 UI 可读性。

### 3.4 只拆真正需要运动的环境层

当时运行时采用以下五层（2026-09-19 已停用并删除文件）：

| 图层 | 文件 | 职责 |
| --- | --- | --- |
| 静态群岛 | `gui/main_menu_layers/islands_static.png` | 承担完整构图、岛屿、渡船和基础水面 |
| 云影 | `gui/main_menu_layers/cloud_shadow.png` | 最慢、最宽的横向明暗变化 |
| 远雾 | `gui/main_menu_layers/far_fog.png` | 以浓淡和轻微聚散制造空间呼吸 |
| 水光 | `gui/main_menu_layers/water_light.png` | 不规则、轻微的水面闪动 |
| 灯火 | `gui/main_menu_layers/lamp_glow.png` | 柔和呼吸，并为右侧菜单建立暖色锚点 |

当时所有图层均为 1920×1080。历史运行路径为 `game/gui/main_menu_layers/`；历史母版路径为 `tools/art_source/main_menu/main_menu_dynamic_master.psd`，本轮均已清理。

### 3.5 Ren'Py 只负责简单、可预测的循环

当时动态代码集中在 `game/main_menu_dynamic.rpy`；该文件现用于进度标题选择，以下为历史实现：

- 四个动态层统一使用 12 秒循环。
- 云影速度最慢、位移最大，但有缩放安全区。
- 远雾以透明度和轻微缩放为主，避免整张贴图平移感。
- 水光使用不同长度的小段变化，避免机械呼吸。
- 灯火只改变明暗，不做位置漂移。
- 动态默认持续播放，不再增加玩家控制项。

统一周期避免多个互质周期叠加成很长的总循环，使完整逐帧验收成为可执行任务。

### 3.6 实际发现并修正的问题

第二版并非一次完成，主要修正包括：

- 云影位移过小：增大横向幅度和明暗变化。
- 远雾像整张贴图滑动：减少平移，改用透明度与轻微缩放聚散。
- 远雾边缘出现矩形接缝：重新处理透明边缘并增加安全余量。
- 水光变化不明显：提高明暗差，改成非等长节奏。
- 菜单深灰字落在深色湖面：改为暖灰亮字配深色描边。
- 空存档位蓝绿色过强：改为低饱和深灰绿。
- 二级菜单退出直接关闭：统一恢复退出确认框。

这些问题说明：静态背景正确不代表主题页完成，必须在实际运行页面中同时观察背景、文字、交互和动态。

## 4. 两次制作的核心经验对照

| 项目 | 第一次 | 第二次 | 固定结论 |
| --- | --- | --- | --- |
| 起点 | 模仿其他作品的动态形式 | 定义“书简湖入局”的叙事情境 | 先回答玩家第一眼要理解什么 |
| 主体 | 人物与书箱 | 渡船、主岛、群岛与孤灯 | 主菜单主体应服务世界与主题 |
| 构图 | 先画人物，后放UI | 灰阶阶段同时预留标题与菜单 | UI必须从构图第一天参与 |
| 分层 | 从完整图中裁局部 | PSD中按运动职责真分层 | 分层必须在绘制阶段完成 |
| 动态技术 | Live2D、帧序列、ATL混用 | Ren'Py五层环境循环 | 选择满足目标的最低复杂度技术 |
| 动态重点 | 眨眼、头发、衣带、衣摆 | 云影、远雾、水光、灯火 | 远景主题优先环境运动 |
| 文件管理 | 多版本、帧序列、调试图进入项目 | 运行时、母版、临时QA分离 | `game/`只放最终运行资产 |
| 验收 | 看少量关键帧后继续修补 | 完整循环逐帧＋实际页面QA | 动态必须验收每一帧和首尾接缝 |
| 结果 | 角色破绽多，主题不清，返工慢 | 空间明确、UI清楚、运行稳定 | 先做正确结构，再做细节 |

## 5. 以后制作全新主题背景的固定流程

### 第一步：写一句叙事命题

格式：

`玩家站在哪里，正在看向哪里，画面暗示他将进入什么处境。`

这句话写不清，不开始出图。

### 第二步：确定 UI 安全区

在 1920×1080 画布上先标记：

- 标题区域。
- 主菜单区域。
- 版本号区域。
- 主要视觉路径。
- 不可被动态高亮反复扫过的文字区域。

### 第三步：制作三张灰阶小稿

每张只允许改变大形、明暗和空间路径，不做材质细节。仅在用户确认采用某张构图后进入下一步；全部否决则记录排除项并重新构图，不要求用户从已否决稿中选择。未采用稿留在生成工具工作区，不进入项目。

### 第四步：制作无字、无菜单的静态定稿

先检查：

- 不依赖文字时是否仍能说明主题。
- 前中后景是否分明。
- 主要主体是否避开菜单。
- 明暗重心是否支持标题和菜单阅读。

### 第五步：在 PSD 中原生分层

只拆会运动的对象。每个动态层必须具备：

- 透明背景。
- 完整遮挡补绘。
- 足够的画布外安全余量。
- 羽化或自然消失的边缘。
- 单独开关时仍可判断其职责。

### 第六步：先做最小动态原型

只启用一个层，确认运动方向、速度、幅度和接缝，再增加下一层。不要同时调四层后再猜是哪一层出错。

### 第七步：统一循环周期

默认优先 8、10 或 12 秒等易验收周期。所有层在统一周期内回到起点，避免产生数分钟才能完整重复的组合循环。

### 第八步：完整逐帧验收

按目标帧率检查完整循环。当前项目标准为 60fps、12秒、720帧。

每帧检查：

- 是否露边、闪白、闪黑或出现矩形边界。
- 图层是否漂移到错误空间。
- 透明度是否突然跳变。
- 首尾是否无缝。
- 多层同时达到极值时是否过亮、过暗或抢文字。

发现异常后，从第1帧重新检查完整循环。

### 第九步：实际 UI 与操作验收

至少检查：

- 标题、菜单、版本号在动态最亮和最暗时均可读。
- 普通、悬停、选中、禁用状态能够区分。
- 当前方案主要主体、标题与菜单的视觉顺序正确，不固定沿用旧方案的场景元素。
- 主菜单到读取、设置、关于、帮助的转场正常。
- 空存档位不抢缩略图。
- 退出始终出现确认框。
- 1920×1080、1280×720和窗口模式没有偏移或裁切。

### 第十步：冻结与清理

项目目录最终只保留：

- 当前采用的运行时图层。
- 一份可编辑母版。
- 一份运行时代码。
- 必要的索引与复盘文档。

帧序列、预览图、局部裁图、调试蒙版和 QA 截图留在临时工作区，验收后按明确路径逐个清理。

## 6. 技术选择边界

### 使用 Photoshop 分层＋Ren'Py ATL

适合：

- 云、雾、水光、光晕、粒子、远景树影。
- 小幅、低频、循环的环境变化。
- 不需要面部或复杂骨骼变形的主题页。

### 使用 Live2D Cubism

仅当以下条件同时满足时考虑：

- 角色是主题页不可替代的核心。
- 原画从一开始按 Live2D 规范拆分。
- 头发、五官、衣物遮挡区域已完整补绘。
- 有明确的参数、变形器、物理和运行时预算。
- 角色运动产生的叙事收益明显高于制作与维护成本。

环境主题不满足以上条件时，不使用 Live2D。

### 使用帧序列或视频

只适合无法用少量分层表达、且画质收益足以承担体积和解码成本的短片段。主菜单无限循环默认不用大量 PNG 帧序列。

## 8. 新人物主题：画面命题讨论记录（2026-09-06）

### 8.1 范围与采用状态

- 用户要求先讨论“画面命题”，检索关键词为“书简湖、陈平安、顾璨”，优先找作者连载到中期及临近收尾时讨论较多的帖子。
- 用户随后要求“记录”。本节保存检索结果与讨论提案，不将其升级为用户已确认的命题、文案、场景或构图。
- 本轮不出图、不建模、不替换运行版；已否决概念图仍按图片索引排除，不因本节讨论恢复。

### 8.2 时间范围与证据边界

重点范围为 **2018 年 11 月中下旬至 12 月中旬**，另保留前期争论作为对照。

### 9.4 动作预算与误读风险

后续优先讨论的微动：陈平安的呼吸、停顿与小幅视线变化；顾璨的轻微转眼或坐姿变化；门外自然光影与少量风动。当前仅为动作意向，未建模、未制作、未逐帧验收。

静态姿态可选“停笔”或“继续处理册页”的瞬间，但首轮动态暂不设计反复写字、翻页、递物、起身走动；这些动作会推进事件，机械循环还会增加手、纸、桌面之间的接触与遮挡风险。尤其不做反复划销名字或“结案”的循环，避免替受害者宣布已获交代。

需避免三种误读：

1. **温馨陪读**：阳光、孩子和书桌消解矛盾，受害者退成装饰。
2. **认错求饶**：顾璨垂头蜷缩、不敢进门，提前完成其悔悟。
3. **公堂审判或主角受难展示**：陈平安居中俯视顾璨、当面崩溃，把复杂关系改成判官与犯人或主角的伟大。

| 选择尚未完成 | 关系焦点清楚，姿态处于可持续的停顿 | 循环演出离开、拒绝、和解等不可自然撤回的事件 |

上述表达不限定为旧小屋、渡口、递炭或跨时点构图。已否决方案仍按图片索引排除；用户未说明的否决原因不补写为确定事实。

### 17.5 制作前的最小验证包

1. **一页剧情与美术简报**：所选时点、脚本依据、人物关系、主情绪、视觉焦点、剧透边界和 UI 需求。事实、设计推导、待确认项分别标注。
2. **一张有用途标注的参考板**：每项说明只参考构图、姿态、光色、时代材质或动态中的哪一项；角色身份仍由既有母版控制。
3. **一张低细节小稿对照**：比较同一命题的不同观看顺序和人物关系。标题与按钮用独立占位同步检查；不把换天气和换颜色当成不同构图。
4. **所选稿的动作边界示意**：确认需要动什么、为何要动、最大幅度和遮挡补绘区域，再进入正式美术与绑定。

建议的评审问题是“先看到谁”“两人像是什么关系”“画面给人什么情绪”“最想继续了解什么”，而非要求未读剧情者猜出所有道德因果。可用短时间观看和缩略图帮助发现问题，但它们是本项目拟用的检查方法，不是经本轮研究证明的统一行业通过标准。真实观众反馈尚未执行，模型自评不能代替玩家理解验证。

与第 16 节共用状态、母版和预览，不新增重复状态文档；本轮只更新本 SOP。选稿后沿用已验证工具链，具体新人物仍需独立进行结构和动作检查。
